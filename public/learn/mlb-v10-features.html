The V10 feature audit: what was broken, what fixing it changed, and how to defend the call

V10's feature table had copies, constants and three inputs that disagreed with what the model was trained on. Fixing them is right. It does not measurably change accuracy, and the numbers below show why. The page is built so you can explain every step to someone who pushes back.

Scope. This page covers collinearity, train/serve skew, and the specific evaluation behind these fixes. It doesn't repeat material covered elsewhere: ML_COURSE explains the algorithms (logistic regression, L1/L2, boosting, calibration, proper scoring rules), ML_LESSONS covers leakage, statistical power and why more features isn't more information, and MODEL_HISTORY covers what V1 through V10 were actually worth.

measured means computed in this audit. inferred means reasoning from the evidence without a direct test.

1. The short version

  • measured The model in production uses 73 features, not 158. train_v10_models.py keeps only the names that exist in the V8 training parquet. None of the buggy xFIP, wOBA or Statcast-percentile columns ever reached the model.
  • measured Three inputs the model does use disagreed with training. This is train/serve skew: season_pct_complete (trained on 0 to 1, served as 1.0 every game), day_of_week (trained 1–7 with Sunday = 1, served 0–6 with Monday = 0) and luck_differential (served with the opposite sign).
  • measured Correcting those three inputs moves walk-forward log loss by +0.0008 (95% CI −0.0014 to +0.0031), which is zero within noise. It changes 163 of 1,963 picks.
  • measured The 3-feature logistic and V10 are statistically tied on log loss in every window. V10's edge at the sharp end is real in direction but not significant: +4.7pp (CI −3.1 to +12.8).
  • Recommendation: keep the V10 model. Ship the builder fixes, because correctness is the default when the numbers are tied, and a flipped sign is a time bomb for any future retrain. Don't swap production.

3. Collinearity: four instruments, four different questions

"The features are collinear" can mean four different things, and each diagnostic answers only one of them. On V10's 158 listed features over 1,963 honest 2026 games measured:

DiagnosticWhat it asksV10 result
Zero varianceDoes the column carry any information at all?16 constant
Pairwise correlation |r|Are two columns near-copies of each other?28 pairs > 0.9, 18 pairs > 0.99
VIF = 1/(1−R²)Can this column be predicted from all the others?126 of 142 have VIF > 5; 90 are effectively infinite
Matrix rankHow many truly independent directions exist?103 out of 142, so 39 exact dependencies
Eigenvalues of the correlation matrixWhich directions carry almost no variance?39 are zero; 62 are below 0.1; the top one is 22.5

Why they disagree

Correlation only sees pairs. run_diff_differential is exactly home_run_diff_10g − away_run_diff_10g, yet its correlation with the home term is only 0.758. No pair looks alarming, but together the three are perfectly dependent.

VIF sees one column against all the others, so it catches that triple, and it is infinite for every column that takes part in an exact identity. VIF is per column, though. It doesn't tell you how many redundant directions there are.

Rank counts redundant directions exactly (39), but it's all-or-nothing. A near-duplicate at r = 0.999 still counts as full rank.

Eigenvalues grade that near-miss. A tiny eigenvalue is a direction the data barely moves in, and any model that tries to estimate a coefficient along it will be guessing. The condition number (largest eigenvalue divided by smallest) is about 1017 here, which is numerically singular.

For contrast, the 3-feature model has VIFs of 1.73, 1.73 and 1.01: Elo and Pythagorean correlate at 0.648, and the SP composite is nearly orthogonal to both. That is healthy.

4. Why collinearity barely hurts trees' predictions but wrecks their importances, and flips logistic signs

Trees: the predictions survive

A tree picks one column per split. If two columns are copies, it doesn't matter which one it picks, because the split is the same. measured Adding an exact copy of pythag_differential to a 3-feature XGBoost gave predictions that correlate 0.974 with the original model's, and log loss moved by only 0.006.

Trees: the importances don't

The credit that one column earned gets split across its copies. Pythagorean importance went from 0.32 to 0.23, and the copy took 0.26. In the full 142-column model, the ranking of importances across 8 bootstrap refits agreed at a Spearman correlation of only 0.27, and the top five features changed completely every time (one refit led with fg_whip_differential, another with home_rested). Never read a V10 importance chart as "what drives wins".

Caveat. "The predictions survive" means they survive collinearity. They don't survive a small sample. The same 8 bootstrap refits of the 142-column XGBoost produced predictions that correlate only 0.53 with each other. That instability comes from too many parameters per game (section 5), not from collinearity.

Logistic regression: signs flip

A linear model has to split one effect across correlated columns. When the columns are nearly collinear, many splits fit the data about equally well, and a small change in the sample moves which one wins. measured Across 300 bootstrap refits of an unregularised logistic on five correlated strength columns:

Elo is still positive in only 68%, because it shares its signal with Pythagorean (VIF 1.73). That is why L1 regularisation is useful: it picks one column and zeroes the other, rather than letting the two trade off.

5. Too many features per game

Each feature a model learns costs estimation variance, and a season gives you about 2,400 games. An earlier 450-trial automated search measured that 3 features beat the top-k subset, which beat all 161 features (log loss 0.6887, 0.6899, 0.6932). This audit reproduced the effect measured. V10's own XGBoost settings, fit on this season's games over 36 deduplicated differentials, scored 0.7572 walk-forward, far worse than always picking the home team (0.6918). It made 684 picks at 64%+ confidence and won only 52.3% of them.

Deduplicating the columns didn't rescue it. Collinearity was never the binding problem for trees. The number of parameters per game was. That's why the served V10 (trained on 24,428 games from 2015–24) and a 3-parameter logistic end up tied: each is a different way of staying under the sample cap.

measured I also rebuilt real season-to-date team xFIP, wOBA, whiff%, fastball velocity, exit velocity, hard-hit% and barrel% from 772k Statcast pitches. Team xFIP had the best single-feature AUC in the whole set (0.565, against Pythagorean's 0.555). Adding all seven to the 3-feature model still changed walk-forward log loss by only +0.0002. The information is real, but it's already in Elo and Pythagorean. So the placeholders were dropped rather than rebuilt.

6. Train/serve skew and placeholder features

Train/serve skew means the model sees a feature computed one way during training and another way in production. It's worse than a bug in a feature the model ignores, because the model relies on the relationship it learned, and at serve time that relationship doesn't hold. A tree that learned "late season plus X means home wins" applied that rule to every April game, because season_pct_complete was 1.0 all year.

How to detect it. Put the served feature's distribution next to the training distribution. measured Training had season_pct_complete at mean 0.505 (sd 0.294), while live was 1.000 (sd 0). day_of_week mean was 4.05 in training and 3.17 live. The correlation of luck_differential with home − away was +1 in training and −1 live. Checking distributions is cheap, and it catches this whole class of bug.

Placeholders (a constant 50.0, or ERA reused as xFIP) do the most harm when a model trains on them: a constant teaches nothing, and an alias double-counts one signal under two names. Here they did no harm only because the training data never contained them. A NULL is better than a fake value, because a NULL is visibly missing and a 50.0 looks like data.

measured The surprising part is that fixing the three skewed inputs didn't help: +0.0008 log loss (CI −0.0014 to +0.0031). inferred Three reasons fit. The model's total signal is only about 0.005 nats, so little depends on any one input. day_of_week and season_pct_complete carry almost no outcome signal (AUC of the true season fraction is 0.509). And by September a pinned 1.0 is nearly correct. Ship the fix anyway. A future retrain on the 2026 table would otherwise learn the flipped sign.

7. Honest pregame evaluation

game_predictions and game_v10_features are also written by backfills after games finish. Taking the latest row per game picks the contaminated ones. Every row in this audit satisfies computed_at < first pitch (for features) or predicted_at < game_time_utc (for served predictions), and the filter runs inside the dedupe. ML_LESSONS covers the leakage story itself.

Models fit on this season are scored walk-forward: the first fit uses 500 games, the model refits every 100, and it only ever predicts games after its training window. Results are reported on three windows:

  • Walk-forward: 1,463 games, 2026-06-03 to 09-24.
  • Last 400: 2026-08-25 to 09-24.
  • Fresh: 220 games after 2026-09-07. No earlier study had seen these, so they are the only games that can't have influenced any choice made here.

9. Accuracy at a confidence threshold vs log loss and calibration

Log loss scores every game and punishes confident misses heavily. It is a proper scoring rule, so it rewards being honest about uncertainty. Accuracy at ≥64% scores only the games a model chooses to be confident about. That's a product metric ("how good are the strong picks?"), but it has two traps:

  1. A calibrated model rarely reaches 64%. On a nearly coin-flip sport, a well-calibrated model is almost never 64% sure. The 3-feature logistic made 5 such picks in 1,463 games, while V10 made 185. Comparing their accuracy "at ≥64%" compares 185 games with 5. So compare equal counts: each model's top 185 most-confident picks.
  2. Easy games are easy for everyone. measured On the exact 185 games where V10 was ≥64% confident, the 3-feature model picked the same side often enough to hit 62.7%, against V10's 64.9%. Most of V10's "sharp end" is the games themselves, not skill only V10 has.

Calibration (whether 60% calls win 60% of the time) is a separate property. ML_COURSE covers it. The practical consequence here: if you ever recalibrate V10, the 64% tier empties, so define tiers by quantile, not by a fixed probability.

10. Bootstrap confidence intervals

A bootstrap resamples the evaluated games with replacement (2,000 times here), recomputes the metric on each resample, and reports the middle 95% of those values. It answers one question: "if the season had dealt a different but equally likely set of games, how much would this number move?"

  • Paired beats unpaired. To compare two models, resample the same games for both and bootstrap the difference. Game difficulty cancels out, so the difference interval (±0.007 here) is much narrower than either model's own interval (±0.009).
  • Scale. With about 1,400 games, a log-loss difference needs to be around 0.007 before it clears noise. The whole modelled signal is about 0.005 nats. This is the evaluation cap: the season is too short to separate these models, and a better model won't fix that.
  • What the bootstrap can't see. It treats games as independent draws from one stable process. It doesn't cover a mid-season drift, or the choices you made after looking at the data (section 11).

11. Selection bias

If you look at many numbers and report the best one, the best one is biased upward. The bias grows with the number of looks, not with anything real. This audit has three places where that applies:

  • The 64% threshold was chosen after V10 was seen doing well there. So the fresh window matters: it's the only test of that claim on games that didn't shape it. The claim held in direction (71.4% on 42 games) and stayed inside noise.
  • Model search. 450 earlier trials converged on the 3-feature model. Its walk-forward score is a slightly optimistic estimate of its future, because the winner of a search is favoured by luck. Earlier holdout work measured that search gap as negative (−0.0066), because three parameters leave little room to overfit.
  • This audit's own choices. I ran 8 model variants and 3 windows and reported all of them, including the ones that went against the fixes. Showing every row, not just the flattering ones, is the defence.

12. How to defend this

"You fixed bugs and accuracy didn't improve. So what was the point?"

Two points. First, the served model was receiving inputs that contradicted its training: a flipped sign, a shifted weekday and a frozen season clock. That it happened not to cost much is luck plus a weak signal, not safety. The next retrain on 2026 data would have learned the wrong sign. Second, the audit found that the headline "158 features" was really 73, and that the 2025 validation score was computed on frozen inputs. Knowing what the model actually is has value by itself.

"The 3-feature model has better log loss. Why not switch?"

It's better on the full walk-forward span by 0.0027 (CI −0.0100 to +0.0048), and worse on the last 400 games and the fresh window by about 0.009 (CIs cross zero). That is a tie. When models tie, you don't pay the switching cost: a new artifact, new confidence tiers, and a product that suddenly shows almost no strong picks.

"V10 hits 65–71% on its confident picks. Isn't that the edge?"

It's the strongest thing V10 has going for it, and its direction held on 220 games nobody had looked at. But on the same games, the 3-feature model gets 62.7% to 66.7%. The difference is +4.7pp with an interval of −3.1 to +12.8. Say "plausible, not proven", and plan to re-measure after a full season of fresh games.

"Why not just implement real xFIP and Statcast team metrics?"

I did, from 772k pitches, strictly before each game. Team xFIP is the best single feature in the set (AUC 0.565). Added to the 3-feature model, all seven moved log loss by +0.0002. The signal is already carried by Elo and Pythagorean. Adding columns costs estimation variance, and the sample is already the binding constraint.

"Collinearity is bad, so why not deduplicate V10?"

Trees are nearly indifferent to duplicates when it comes to predictions: an exact copy still gave 0.974 prediction correlation. Deduplicating matters for interpreting the model (importances, coefficient signs), not for accuracy. The season-fit XGBoost on deduplicated features was the worst model here (0.757), because the problem was sample size, not redundancy.

"How do you know the evaluation isn't contaminated?"

Every feature row was computed before first pitch, every served prediction was made before first pitch, and the guard runs inside the dedupe. Season-fit models only predict games after their training data. The fresh window postdates every earlier study. The served predictions reproduce from the stored features at a correlation of 0.992, which confirms the stored inputs are the ones that were served.

13. Glossary

Log loss
Average of −ln(p assigned to what actually happened). A constant 50/50 guess scores 0.693. Lower is better. It's a proper scoring rule.
Walk-forward
Train on the past, predict the next block, add that block to training, repeat. Mimics production and never uses the future.
Holdout
Games held back from every modelling decision, scored once at the end.
Train/serve skew
A feature computed differently at training time and at prediction time.
Placeholder feature
A column filled with a constant or with a copy of another column because the real data was missing.
Collinearity
Some features are (nearly) linear combinations of others.
VIF
Variance inflation factor, 1/(1−R²) from regressing one feature on all the others. Above 5–10 is a concern; infinite means an exact dependency.
Matrix rank
The number of linearly independent columns. Columns minus rank equals the number of exact dependencies.
Eigenvalue (of the correlation matrix)
The variance along one principal direction. Near zero means a direction the data barely moves in, where coefficients can't be estimated.
Condition number
Largest eigenvalue divided by smallest. Huge values mean small data changes cause large coefficient swings.
Feature importance (gain)
How much a tree model's loss improved on splits using that column. It gets split arbitrarily among duplicates.
Bootstrap CI
The 2.5th to 97.5th percentile of a metric recomputed on resamples of the games.
Paired comparison
Scoring two models on the same resampled games, so that shared difficulty cancels.
Sharp end / confidence threshold
The subset of games a model is most confident on. Compare models at equal counts, not at equal probability cut-offs.
Calibration
Whether stated probabilities match observed frequencies.
Selection bias
Upward bias from reporting the best of many looks, or from choosing a subset after seeing it perform.
Backfill contamination
Rows written after the outcome was known, which silently inflate evaluation if they aren't filtered.
